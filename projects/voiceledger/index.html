Overview

In many organizations the daily report is given out loud and then lost. VoiceLedger lets a member record a voice message in the Bale messenger; the system checks that an admin has approved the sender, downloads the audio, transcribes it to Persian text and stores it in a searchable, multi-domain knowledge base. A REST API exposes the stored reports.

The backend was built from scratch with an asynchronous design and a versioned database schema, and the speech recognition runs locally, so the audio never leaves the server.

Approach

  1. 1

    Receive

    A Bale bot (a Telegram-compatible API) handles /start, /help and voice messages; new users register automatically but cannot submit until an admin approves them.

  2. 2

    Track the report

    Each report moves through pending, downloading, downloaded, transcribing and completed (or failed), with an error message and a retry counter.

  3. 3

    Transcribe

    faster-whisper with the small model on CPU (int8), voice-activity filtering and deterministic decoding to reduce hallucinations, run in a worker thread so the bot is never blocked.

  4. 4

    Store atomically

    In one database transaction the transcript is saved, the report is completed and the matching knowledge entry is created.

  5. 5

    Serve

    A FastAPI REST API under /api/v1 with routers, dependency injection and response models, plus health endpoints that check the database.

Key decisions

Approval gate and roles

A role model (super admin, domain admin, operator) and admin approval keep unknown users from adding data.

One commit for completion

A report can never be 'completed' without its knowledge entry, or the other way round.

Local speech recognition

No audio is sent to an external service; the trade-off is CPU time, handled with a worker thread and async processing.

Versioned schema

Five Alembic migrations, including a backfill for existing rows, so the database can evolve safely.

Domains from the start

Reports and entries belong to a domain, with a seeded default, so the system can serve several teams.

How it works

Voice message in Bale→Approved user?→Download audio→Faster Whisper (Persian)→PostgreSQL knowledge base→Reply with text and tracking ID

Limitations, stated openly

  • The API does not authenticate requests yet and audio is stored on local disk.
  • There is no background queue with automatic retries: failed reports keep their error message and retry count, but retrying is manual.
  • No accuracy measurement of the transcripts is reported.

What is next

  • JWT or API-key authentication with role-based permissions on every endpoint, and in-bot admin commands.
  • A job queue (Celery, ARQ or RQ) with retries and backoff.
  • Structured logging and metrics (Prometheus, OpenTelemetry).
  • Object storage (S3 or MinIO) for audio, and semantic search and RAG over the knowledge base.
