Overview

Screening resumes by keyword rewards the candidates who copy the wording of a job post, not the ones who fit the role. This service evaluates a candidate's resume (PDF or DOCX) against the job description and the requirements of the specific team, and returns a match score from 1 to 10 together with the evidence that justifies it.

It is built as a small, decoupled system: a FastAPI REST service that does the work, a Streamlit MVP on top of it, and a model layer that is independent of any single LLM provider. The project is still in progress, so this page describes the design rather than final results.

Approach

  1. 1

    Parse the resume

    PDF and DOCX files are parsed into structured text, so the model sees sections (experience, skills, education) and not a raw dump.

  2. 2

    Process the requirements

    The job description and the team-specific requirements are turned into a checklist that the evaluation can be held against.

  3. 3

    Score with evidence

    An LLM compares resume and requirements and produces a 1 to 10 match score. Every score comes with evidence-based reasoning that points to the parts of the resume it relies on.

  4. 4

    Report

    The result is available through the REST API and as a downloadable PDF report.

  5. 5

    Interface

    A Streamlit MVP, decoupled from the API, lets recruiters try the service without writing code.

Key decisions

Evidence instead of keywords

A number alone cannot be trusted or challenged. Requiring reasoning with evidence lets a recruiter check why a candidate scored 4 or 8.

Provider-agnostic model layer

The service talks to the organization's internal LLM API through a configurable provider interface, so the model can be switched without touching the scoring logic.

Structured, validated outputs

Model answers are parsed into Pydantic models; an answer that does not fit the schema is caught and retried rather than passed on.

Operational basics from day one

Retry and timeout handling, plus logging of latency and token usage per request, so cost and speed are visible from the first prototype.

API first, UI second

The Streamlit MVP is a thin client of the REST service; other tools can reuse the same API.
