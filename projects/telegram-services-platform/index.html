Overview

A Telegram bot where users buy digital services with coins. The hard part is not the chat but the money: wallets, orders and an external provider have to stay consistent even when the provider fails, a button is pressed twice or an order is only partly delivered.

The platform is an asynchronous Python backend (aiogram 3, FastAPI, PostgreSQL, Redis) with a wallet, an order engine, an integration with the RapidSeen SMM API and bilingual (Persian and English) bot flows.

Approach

  1. 1

    Wallet

    Coin balance per user with atomic credit and debit and a full transaction history (credit, debit, refund, adjustment); insufficient balance raises a dedicated error.

  2. 2

    Orders

    Each order has a tracking code (ORD-YYYYMMDD-XXXXX) and an idempotency key, and keeps a snapshot of its price and service.

  3. 3

    Placement

    Debit the wallet, create the internal order, call the provider; if the provider fails, refund automatically and mark the order failed.

  4. 4

    Lifecycle

    A background job checks open orders at the provider and maps their status to the internal states.

  5. 5

    Refunds

    Partial and canceled orders are refunded in proportion to what was not delivered, once only.

  6. 6

    Bot flows

    Single and multi-post ordering with a state machine, link validation, order list and tracking, forced channel join, user registration.

Key decisions

Idempotency keys

A second press of the confirm button reuses the key and is rejected as a duplicate, so nobody is charged twice.

Proportional refund

refund = cost × remains ÷ original quantity, rounded half-up to whole coins, applied once (double-refund protection), and only when the remaining quantity is known.

Cancel is a request

Asking the provider to cancel does not mark the order canceled; the final status comes from the next status check.

Layers

Handlers call services, services call repositories; the SQL lives in one place, and the provider client is injected so it can be mocked.

Decisions written down

The assumptions behind refunds, rounding and cancel semantics are logged in the repository.

Limitations, stated openly

  • The ordering flows are covered by unit tests but have not yet been run end to end against a live provider account.
  • The service id and the price of the 'view' service are placeholders to be replaced from the provider's service list.

What is next

  • Run the complete flow once with a test bot, a test database and a provider test account.
  • Move prices and service ids to the provider's real list.
  • Admin features: manual wallet adjustments and order search.
